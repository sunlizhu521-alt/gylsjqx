# 供应链数据清洗

一个纯前端、可部署到 GitHub Pages 的数据处理工具台。文件会在浏览器内存中读取和处理，不会上传到服务器。

## 本地启动

```powershell
python -m http.server 8899
```

访问：

```text
http://localhost:8899/
```

## 发布成可分享网站

1. 在 GitHub 创建一个新仓库，例如 `data-processing-center`。
2. 把本目录内容推送到仓库的 `main` 分支。
3. 打开仓库 Settings -> Pages。
4. Source 选择 `GitHub Actions`。
5. 等待 Actions 跑完，访问：

```text
https://你的用户名.github.io/data-processing-center/
```

也可以不用 Actions，直接在 Settings -> Pages 里选择 `Deploy from a branch`，分支选 `main`，目录选 `/root`。

## 已支持

- 内部交易对账单：导入采购入库明细，填充内置模板，按采购组织分别下载 Excel 和 PDF
- 付款节奏跟进：核对资金台账、付款申请汇总、谈判付款和 OA 流程，导出整理结果
- 资金台账整理：读取采购付款台账的五个人员明细，汇总全部月份导出一张正常付款表；可选上传原始 OA 流程表，补充当前节点、未操作者、流程状态和是否已付款
- 季度预算整理：五个本地文件槽位，合并去重或继续人工明细，按本笔分期核对付款状态，导出明细与两组预算汇总
- 采购入库单签字：上传多份采购入库单，自动签字并合并为 A4 竖向 PDF
- 检验报告单-电子章：上传报告图片，旋转后加盖内置质检合格章，下载 JPG；切换工具保留本次图片
- 备货分配：按采购分工整理备货需求，并按采购下单人导出
- 订单履约表整理：合并指定工作表、对比上次数据并导出汇总
- 合同生成：上传订单和 Word/Excel 模板，手动映射并在浏览器本地生成新合同
- 付款申请单整理：按付款主体汇总付款明细，优先一页，明细较多时清晰分页，生成 Word 和 PDF

所有工具直接在首页内显示，切换时保留本次内容。首次打开默认进入“付款节奏跟进”；后续打开或刷新时恢复上次使用的工具，旧记录中的已移除工具会回到“付款节奏跟进”。页面宽度随浏览器自动适配。

“付款节奏跟进”的核对选项显示对应来源文件名，OA匹配候选继续显示候选来源。下载名称为“付款节奏跟进-YYYY-MM-DD-V版本号.xlsx”，沿用原有每日版本计数；兼容原“资金整理”文件中的本工具申请日期批注，更新时保留人工批注。

“付款节奏跟进”导出的谈判付款表，将工具处理的数字日期表头保存为完整的年月日文本，选中表头和金额时日期不参与求和，再次上传仍按原日期识别。正文金额及金额公式保持数值；人工自定义保留列不变。`npm run test:funds-date-headers-browser` 验证日期表头、金额、重复导出及重新上传。

“资金台账整理”只纳入“是否谈判付款＝否”的记录，已结清及无OA号的记录也保留，不修改源表状态。应付款时间优先取“应付款时间／应付时间”，空白再取预估时间；应付时间和预估时间均为空时（包括预估列缺失或单元格空白），按所属月份月末＋账期天数＋7天推算（月账期按30天/月），仅用于排序，输出应付款时间为“未对账待定”。有明确日期时仍按年月日显示。行按“是否提交纸质付款审单”中文名称降序排列：已提交、未提交、待核对、空白；同状态按应付款时间升序，同日保持来源顺序；日期无法识别或缺少有效月份、账期而无法推算时保留原记录并提示来源，在同状态内排在有效日期之后。原始OA表兼容“流程编号／流程编码”，按台账OA号精确匹配；同号流程信息一致只读取一次，冲突或缺号、未找到时待核对。“归档／已归档”为已付款，“未归档”为未付款，其他状态待核对，不根据“办理人执行”判断付款。未上传OA时四个流程字段留空。“已付款”记录预览及导出整行标浅红（#FF9999），使用可手动修改的普通填充色。采购跟单员取来源台账工作表对应的人员姓名，兼容带日期后缀的表名。输出一张“正常付款”，14列为采购跟单员、供应商、付款主体、对公付款OA流程号、申请付款金额、摘要、应付款时间、当前节点、未操作者、流程状态、是否已付款、申请付款月份、需要提交付款审单的日期、是否提交纸质付款审单。可选上传“付款申请单汇总”，仅按OA号判断纸质审单：匹配为已提交，未匹配为未提交，台账缺号或多号为待核对，未上传留空。优先读取同名“付款申请汇总”sheet，否则要求唯一表头候选；编号列依次优先流程编码、流程编号、合同号，不按单元格空白回退。重复OA号不增加付款记录或金额；无效编号提示来源，编号公式结果异常阻止使用。三个上传槽位保持一行，窄屏横向滚动，替换或移除后重新计算。新增提交日期按北京时间计算：下周及以后取应付日期所在周的上一周周一，本周和逾期款取本周周一；已提交或已付款仍显示。明确预估日期可用于计算，只有年月或“未对账待定”则留空并提示来源。申请付款月份从提交审单日期生成，保存为真实日期、仅显示年月；无具体提交日期时两个字段都留空。取消汇总月份筛选，跨月明细全部保留。每次整理及下载时重算，预览与导出一致。核心 `build` 支持可选 `today: YYYY-MM-DD` 基准日期供确定性测试，默认北京时间当天。下载名称为“资金台账整理-YYYY-MM-DD-V1.xlsx”，日期取北京时间，同一天在当前浏览器成功发起下载后递增，生成失败不递增。文件替换或读取失败清除旧结果。`npm run test:funds-ledger-browser` 使用合成数据检验首页上传、跨月和缺日期记录、预览、切换保留和下载回读；`QA_URL` 指定站点，`QA_OUT` 指定仓库外验收目录。

## 订单履约表整理：系列对比

完整下载增加“系列对比”工作表，读取徐英、操思敏、邢芳芳、李奇四张人员表（兼容日期后缀），按原表的采购下单人、事业部、销售分渠道、系列联合汇总未交付数量。六列为采购下单人、事业部、销售分渠道、系列、上期未交付数据、本期未交付数据；采购下单人取原字段，不使用来源工作表名替代。

上期和本期沿用当前浏览器保存的两次有效上传。显示两期分组并集，某期没有该分组时填0；首次没有上期时该列留空。数量按十进制精确汇总，导出为数值，不含公式。刷新恢复、重复上传不推进历史、异常文件不替换历史的规则继续适用。原文件已有“系列对比”时，将原表保留为唯一的“系列对比（原表）”备份，本次结果仍使用固定名称。事业部分下载和合并核对专用下载保持原范围。

`npm test` 包含分组、空值、零值、小数、异常和历史回滚验证；`npm run test:fulfillment-series-browser` 使用合成文件验收上传下载、历史恢复、格式和同名原表保留，可通过 `QA_URL` 指定站点。

## 内部交易对账单

首页选择“内部交易对账单”，每次导入最新 `.xlsx` / `.xls` 采购入库明细。按表头读取供应商、采购组织、入库日期、物料编码、物料名称、实收数量、含税单价、价税合计及备注；原文件不修改，上传文件不持久缓存，切换工具保留本次内容。

内置 `assets/internal-statement-template.xlsx`。同一采购组织、供应商、月份内，同物料编码和原始含税单价合并数量及价税合计，备注去重合并。物料编码保留文本；单价显示两位小数，汇总金额始终取源表价税合计。每个采购组织分别下载一份 Excel 和一份 A4 竖向 PDF，多个供应商或月份在同一文件内分表、分页；签名及盖章处留空。

“一键下载全部 PDF（ZIP）”按采购组织、供应商和月份逐份生成 PDF，一次打包下载。文件名采用明确简称，例如 `迈德斯特&瑞朗德-2026年6月.pdf`；未配置简称的公司保留全称，重名文件追加序号，正文始终保留公司全称。所有 PDF 生成并校验页数后才下载，失败不输出残缺压缩包。

对账日期默认取各份对账月份的次月 10 日，仍可手动修改。打印预览可按采购组织、供应商和月份选择，与上方“选择对账单”同步。切换保留各份手填信息并回到第一页；切换组织时自动选取该组织的第一份对账单。生成失败会清空旧画面并显示原因。预览选择不改变按采购组织下载的范围。

底部余额、收款、费用、欠款与货款汇总可手填，未填留空；只有相关四项金额全部填妥才计算底部余额合计。新文件会重建结果及手填信息。必填字段异常或源表总计不一致时提示位置并阻止生成。

`npm test` 验证金额、分组、空白和异常数据。`npm run test:internal-statement-browser` 在本地 HTTP 服务验证首页上传、预览、切换保留、逐组织下载及重新上传；默认使用合成数据，可用 `QA_URL` 指向线上。真实样表仅允许通过 `QA_SOURCE` 在本地验收，输出用 `QA_OUT` 指向仓库外目录。

## 付款申请单整理

侧栏进入“付款申请单整理”，上传 `.xlsx` 或 `.xls` 付款明细，选择工作表，核对各付款主体后生成预览。内置 `assets/payment-template.docx`，也可上传同结构 `.docx` 替换。无需服务器处理或额外安装。

三个上传区分别为付款明细、付款申请模板、供应商名录，每项显示本次文件成功读取的引用时间。引用时间不是文件修改日期；切换工具或工作表不重置，重新上传/恢复内置模板时更新。三个上传文件及引用时间保存在当前浏览器的 IndexedDB 中，刷新或重新打开后自动恢复；不会上传服务器。页面提供“清除上传文件缓存”；移除名录会同时删除其缓存，恢复内置模板会清除自定义模板缓存。浏览器禁止存储或空间不足时显示保存失败提示，本次文件仍可使用。手工填写的申请信息、确认勾选和生成结果不缓存，恢复后需重新核对生成。

可上传供应商名录 Excel，并选择工作表、供应商全称列。银行名称取“收款银行”或“收款银行名称”，卡号只取“收款账号”。按供应商全称精确匹配（仅忽略两端空格），名录包含付款主体时同时核对主体。优先引用名录，与原明细不同须勾选确认；也可选择仅补空白。同名不同账号拦截，内容相同的重复记录可匹配。未匹配时提示并沿用原明细，二者均缺失则阻止生成；名录公式错误、长数字精度风险会提示。原明细与最终引用值、来源行并列显示，文件本身不被修改。上传名录时付款明细可不含银行信息列。

- 表头使用“付款申请单信息”中的字段：申请日期、付款主体、申请部门、经办人、付款总金额、供应商全称、开户银行及账号、合同编号、合同总金额、已付金额、本次申请付款金额、票据状态、付款事由、备注。允许表头前有空行。
- 按付款主体分组，不合并或删除重复明细；按“本次申请付款金额”逐笔合计，金额以整数分计算。顶部小写、顶部人民币大写、底部合计使用同一个结果。“付款总金额”不参与汇总，也不再显示差异核对提醒。本次申请付款金额为 0 的记录不进入预览及导出明细；剩余明细按原顺序重新编号，全为 0 时不生成空白申请单。
- 申请日期、部门、经办人可修改；同主体有不同值时必须填写统一值。计划付款日期可填写，空白时保留模板占位线。付款类型固定“采购货款”、付款方式固定“对公转账”。
- 未引用供应商名录时，申请单银行栏整理为“单位:收款单位名称”和“账号:收款账号”两行，保留账号原有空格，省去开户行及行号；无法明确识别或有多个不同账号时保留原文，避免错误选取账号。原始明细核对区保留完整信息。审批签字、财务办结文字、空栏及“一、三、四”编号保持模板内容，不修改上传源文件。
- 同步 NB-gongju 的清晰排版：每个主体优先排入一页 A4 横向，明细默认 10.5 pt，先压缩审批及办结区域，再按需将明细降至最低 9 pt。仍放不下时自动分页，重复抬头、基础资料及明细表头，序号连续，合计、审批及办结仅放末页；单条内容过长时提示调整，不截断内容。预览显示页数及明细字号。
- Word 为可编辑的真实 DOCX；PDF 是高分辨率固定打印版，内容已按 85% 缩放，打印应选择实际大小/100%。不同 Word/WPS 或字体替换可能改变分页，固定打印以 PDF 为准。
- 识别到异常金额、缺少主体、公式错误或长编号数字精度风险时，显示源行，修正后重新上传。其他明细空白及“/”原样保留。输入变化会立即使旧下载失效。

### 开发与验证

本项目是静态网站，无生产打包步骤。无需安装依赖即可运行 `npm test`（金额/分组回归）及 `npm run check`（脚本语法）。使用本地 HTTP 服务预览，不能直接通过 `file://` 读取内置模板。

浏览器验收：先启动 `python -m http.server 8899 --bind 127.0.0.1`，在已有 Playwright 环境运行 `npm run test:browser`。可通过 `PLAYWRIGHT_MODULE` 指定现有 Playwright 包路径、`CHROME_PATH` 指定现有浏览器、`QA_URL` 指定本地网址、`QA_OUTPUT` 指定仓库外输出目录。测试使用虚构数据，不包含真实付款资料。付款排版专项验证使用 `npm run test:payment-layout-browser`，覆盖单页、多页、合并 Word、全部明细及审批办结完整性，并保存排版样本。

浏览器测试覆盖样例导出、大小写金额、固定选项、明细保留、模板替换、异常拦截、工具切换、XLS、移动端和清晰分页。还需使用 Word/WPS 或 LibreOffice 渲染排版测试生成的 `combined-76-rows.docx`，用 `tests/payment-docx-verify.py` 核对实际页数、全部明细及末页办结栏；不能只依据预览或 PDF 页数判断 Word 分页。

渲染后运行 `python tests/payment-docx-verify.py assets/payment-template.docx /tmp/qa/stress.docx /tmp/render/stress.pdf`（按实际路径替换；验证环境需有 pypdf），检查实际页数、全部明细、银行账号、审批及办结文字与保留的模板包成员。

`payment-core.js` 负责金额与分组，`payment-document.js` 负责模板和共享排版，`payment-tool.js` 负责界面。新增 PDF 依赖为本地 vendored pdf-lib（MIT 许可证见 `vendor/pdf-lib.LICENSE.md`）；公用模板之外的真实明细和验收文件不得提交到仓库。

供应商名录字段规则：银行名称优先取“收款银行”，为空时取“收款银行名称”；卡号只取“收款账号”，不引用“银行账号”或银行行号。输出在“开户银行及账号”同一列，显示“银行名称”和“卡号”两行。名录有付款主体时按主体与供应商全称共同匹配；“浙江迈德斯特医疗器械科技有限公司”与“迈德斯特”采用显式对应，申请单使用简称，其他主体不自动猜测简称。

下载按付款主体分别生成单页 Word 和 PDF，预览可同时展示多个主体。文件名为“计划付款日期＋付款主体简称＋该主体本次申请付款金额合计（两位小数）”，如 `2026-09-25迈德斯特2205.00.docx`；计划付款日期未填时提示补填并重新生成，不使用申请日期替代。

## 合同生成

PDF 转换组件支持主动就绪检测，避免组件漏发初始化通知时一直等待；页面分别显示加载、读取合同和生成 PDF 的阶段。加载失败或转换超时会清理失效组件，再次点击生成即可重试，无需重新上传。`npm test` 覆盖消息就绪、超时和重试；`node tests/contract-converter-browser.cjs` 使用虚构订单从首页验证真实转换、预览与连续下载（可用 `QA_URL` 指定首页）。

访问 `contract.html`，上传 `.xlsx` / `.xls` 订单明细和 `.docx` / `.xlsx` 合同模板。文件只在浏览器本地处理，程序不会覆盖或改名原文件。订单仅读取合同编号、序号、物料编码、名称、规格型号、SKU、单位、数量、含税单价、备注、交货时间，以及用于核对的原表含税合计和人民币大写；其他订单信息不读取或映射。映射页不展示模板结构，按这些业务字段列出订单列选择框；模板写入位置根据字段标题自动识别。序号无需选择订单列，只按识别到的物料明细自动生成 1、2、3……；交货时间作为合同单值单独映射和填充。每行金额按数量乘含税单价采用十进制定点运算、四舍五入到分，再汇总得到“含税运合计（小写）”，“含税运合计（大写）”由同一汇总值自动转换为人民币大写；两项不再选择订单列，数量、单价的空值、负数、非数字或超过8位小数会阻止生成并指出源行。原表含税合计和人民币大写只用于核对，差异会提示，不覆盖计算结果。确认文件名和映射后，页面先生成新的 DOCX 或 XLSX 副本，再使用浏览器内的 ONLYOFFICE WebAssembly 转换组件生成 PDF；PDF 按 A4 页面宽度自适应并完整展示当前页，多页使用上一页、下一页翻阅，确认后才能下载合同和同一份 PDF。

映射方案按模板 SHA-256 指纹保存在当前浏览器，也可以导入、导出 JSON；不缓存订单、合同模板和生成结果。订单存在“序号”“行号”或“明细序号”列时，以其中的数字序号行作为物料明细并逐行生成，交货地点、交货时间等尾部信息行不会占用物料序号；没有序号列时再依据物料编码、名称、SKU等映射判断。同名订单或模板修改后可以直接重新选择上传，不会继续使用上一次的文件内容。单值来源出现多个不同值时仍需明确选择取第一条、合并去重或求和。Word 模板暂不支持文本框、图片、域、修订和嵌套表格；Excel 生成直接修改目标工作表 XML，原有图形、数据透视表、结构化表及其他未映射部件原样保留。当前合同 Sheet 含数据透视表时不允许扩展明细行；普通公式会随明细行数自动复制、下移并调整本 Sheet 及跨 Sheet 引用，数组公式或共享公式穿过明细行时才会明确停止。宏、外部链接和受保护文件继续拒绝。PDF 转换通过 `edit.chaxus.com` 提供的纯前端 ONLYOFFICE 编辑器运行，合同字节通过浏览器 `postMessage` 交给转换 iframe，不经过本项目服务器；该组件采用 AGPL-3.0。转换结果会先校验并在异常时自动重试；先使用两个 PDF.js 版本解析，仍无法完整读取时改用浏览器本地 PDFium WebAssembly 逐页渲染，不再使用会裁切页面的内置 PDF iframe。PDFium 包装层为 MIT，内核为 Apache-2.0，许可证见 `vendor/pdfium-2.15.1-LICENSE.txt` 和 `vendor/pdfium-2.15.1-PDFIUM-LICENSE.txt`。转换结果以 ONLYOFFICE 的字体与排版引擎为准，不承诺与 Microsoft Office 逐像素一致。

当模板中存在“合同条款”行，且右侧内容明确匹配内置的标准采购合同条款时，生成副本会完整写入第 1—9 条；其他合同条款不做替换。Word 会取消该行的固定高度、禁止跨页及文字不换行设置，使条款按内容自动增高并可跨页完整显示。Excel 会自动换行并按内容调整条款行高，打印设置固定为 A4、单页宽度；物料明细不超过 8 行时同时尽量压缩为一页，超过时允许纵向分页，不能通过截断文字强行塞入一页。原模板文件始终保持不变。

## 季度预算整理

首页选择“季度预算整理”。五个文件槽位为谈判付款、资金台账整理、预估预算、付款状态依据（可选）、已有付款汇总明细（可选）。“新建整理”需前三项；“继续已有明细”需最后一项，以该表为准保留人工金额、月份、分类、备注和记录。每项支持一个 60 MB 以内的 `.xlsx` / `.xls` 文件，显示引用时间、识别工作表及读取状态。

支持原始谈判分期、已整理月份明细、人员预算收集表及已整理预算。跳过空白、合计和旧备份；合并备注、补充说明及账期，保留零金额、缺失值和异常日期。无法确定年份或分期对应时保留原记录并提示，不根据文件名补造日期或金额。

新建按“谈判付款 → 正常付款 → 预估付款”确定分类和优先级，只自动删除跨来源、有效 OA 号与金额均相同的记录；同来源各分期全部保留，空 OA 或空金额不自动删除。其他疑似重复相邻排列且整行标红，默认保留，可在明细或核对区确认保留/剔除；剔除原因写入备注。页面可查看自动删除清单。

付款依据优先对应本笔的金额单元格。第一项已是付款节奏表时自动复用，也可另传最新依据；同一依据不得支付多行。明确状态或对应分期金额红底才能证明已付，红字开票信息、历史流程和同 OA 的其他分期不算本笔凭据。歧义、冲突及无证据的新记录标“待核对”。已有明确已付不会被较弱的待核对流程信息覆盖。

文件字节、引用时间与人工选择仅保存在独立 IndexedDB `gylsjqx-quarter-budget-files`，不上传服务器。刷新后校验文件指纹再恢复有效选择。替换、移除、读取失败或切换模式清除旧结果/选择；“清空本工具文件与选择”不影响其他工具。浏览器拒绝缓存时显示原因，本次读取仍可用。

下载 `季度预算整理-YYYY-MM-DD_V1.xlsx`，日期取北京时间，当日成功发起下载后版本递增。导出两张表：“付款汇总明细”11列；“付款预算汇总”在同一张表放置月份＋分类、月份两组汇总，备注为空，均为固定值，无公式。按整数分统计未剔除记录，已付只统计“已支付”，未知年月单列“月份待核对”。原日期和金额值保留，显示金额两位小数。居中、换行、边框、冻结表头；明细普通筛选、全部记录默认可见。网页筛选只改变显示，导出仍包含全部整理结果；下载不自动打开。

`npm test` 包含导入、跨表去重、同表分期、付款证据分配、汇总和 Excel 回读验证。`npm run test:quarter-budget-browser` 使用合成文件验证上传、人工核对、缓存恢复、失败失效、筛选和下载；可用 `QA_URL` 指向实际站点，`QA_OUT` 指向仓库外验收目录。真实付款文件只用于本地验收，不加入仓库或线上测试。
